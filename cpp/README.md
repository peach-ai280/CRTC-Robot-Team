# C++ 版：运动 / 机械臂 / 视觉

> 这一套是应你"理论上应该用 C++"的要求写的。我在下面先把**该不该用 C++**
> 的判断讲清楚，再逐份说明每个文件是干什么的、你要对它们做什么。

---

## 一、先说判断：固件用 C 是对的，但不是因为"懒"

你说"理论上应该用 C++ 吧"——这个直觉**一半对一半不对**，我分开说：

**不对的一半**：STM32 固件本体用 C 是工程上的正解，不是退而求其次。

- HAL 库、CubeMX 生成的代码、ST 的所有例程全是 C API。用 C++ 只是给 C 函数包一层壳，没有实际收益。
- 关掉异常和 RTTI（否则 64KB Flash 顶不住）之后，C++ 能用的就只剩"类 + 内联"。而这套代码压根没有复杂的类层次，封装带来的收益接近零。
- 队友接手、老师检查代码时，C 的门槛低得多。

**对的一半**：**算法层和离线验证用 C++ 确实更好**。这也是我写这一套的原因：

1. **一套代码两个目标**。`hal_mcu.cpp` 和 `hal_sim.cpp` 是同一个接口的两份实现，同一份 `chassis.cpp` / `arm.cpp` / `vision.cpp` 换个文件就能在 PC 上跑。C 版做不到这点——C 版的仿真是另写了一份 `sim_kinematics.c`，等于同一套公式写了两遍，**真机代码和仿真代码会慢慢跑偏**，这是个真实的长期隐患。
2. 参数做成结构体，以后要"扫一组参数看哪个最好"很方便。
3. 类的边界（底盘 / 电机 / 舵机 / 序列器 / 视觉）比 C 版的文件划分更清晰，出问题好定位。

**所以结论**：两套并存，各干各的——

| 场景 | 用哪套 |
|---|---|
| 打比赛、接 PS2 手柄 | **C 版**（`firmware/build/full/firmware.bin`） |
| 学逻辑、改算法、离线验证参数 | **C++ 版**（这一套） |

⚠ **C++ 版目前没有接 PS2 手柄**，只收串口字符命令。它不替代 C 版，是给你验证和试参数用的。

⚠ **两套的参数必须同步改**：`firmware/Core/Inc/config.h` ↔ `cpp/src/params.cpp` 一一对应。只改一边会出现"同一个动作两套表现"的怪事。

## 二、上一轮给的那些文件，分别是啥？哪个才是要烧进去的？

**只有 `.bin`（或 `.hex` / `.elf`）是烧进芯片的东西。`.c` / `.h` / `.py` / `.md` 都不是**——它们是"原料"，编译之后才变成能烧的文件。

| # | 文件 | 它是什么 | 要烧吗 | 你要干啥 |
|---|---|---|---|---|
| 1 | `firmware/构建烧录与测试.md` | 说明书：怎么编、怎么烧、三个测试固件怎么用 | ❌ 不烧 | **照着做**。第一步就看这个 |
| 2 | `firmware/Core/Inc/config.h` | **全车唯一调参入口**，每个宏后面都写了"调大/调小的后果" | ❌ 不烧（它是被编进去的原料） | **调试期间 95% 的时间只改这个文件**，改完重编 |
| 3 | `tools/build.py` | C 版构建脚本（本机没 make，用 Python 直接调编译器） | ❌ 不烧 | 在**仓库根目录**敲 `python tools/build.py full`（别在 `cpp/` 里敲，那里没有 `tools/`） |
| 4 | `firmware/Core/Src/test_motion.c` | 底盘测试固件的**源码** | ⚠️ 编译后烧它的 `.bin` | 架空车，串口发 `w/a/s/d/q/e` 看轮子转向 |
| 5 | `firmware/Core/Src/test_arm.c` | 机构测试固件的**源码** | ⚠️ 编译后烧它的 `.bin` | 发 `1`~`7` 试姿态，`i/k` 微调角度 |
| 6 | `firmware/Core/Src/test_vision.c` | 视觉测试固件的**源码** | ⚠️ 编译后烧它的 `.bin` | 不接摄像头也能测：发 `t/y/n` 造自造帧 |
| 7 | `firmware/Core/Inc/hal_shim.h` | 我自己写的 HAL 兼容层（官方库下不下来） | ❌ 不烧（被编进去） | **不用动**。业务代码一行没改就跑起来了 |
| 8 | `firmware/build/full/firmware.bin` | **★ 唯一真正烧进芯片的文件**（完整版，带 PS2） | ✅ **就是它** | 用 CubeIDE 或 STM32CubeProgrammer 烧到 `0x08000000` |

### 四个 `.bin` 不是都要烧，是按阶段换

```
第 1 天  firmware/build/motion/firmware.bin  → 架空车，只验证底盘转对不转
第 2 天  firmware/build/arm/firmware.bin     → 只验证舵机和机构
第 3 天  firmware/build/vision/firmware.bin  → 只验证视觉串口解析
打比赛   firmware/build/full/firmware.bin    → 全部功能，接 PS2 手柄
```

每次换固件就是重新烧一遍，芯片里同一时刻只有一个程序。

## 三、C++ 版每一份文件：干啥的 + 你要干啥

| 文件 | 干什么的 | 你要对它做什么 |
|---|---|---|
| `cpp/inc/crtc.hpp` | 全部类的声明 + `Params` 参数结构 + 硬件抽象层接口 | 读一遍理解结构，**一般不用改** |
| `cpp/src/params.cpp` | 默认参数表（和 `config.h` 一一对应） | ⚠️ **标定后把实测值抄回这里** |
| `cpp/src/chassis.cpp` | 底盘四步管线：斜坡 → 限自转 → 麦轮逆解 → 归一化 | 一般不用改 |
| `cpp/src/motor.cpp` | 单轮输出：死区补偿 → 起步助力 → 电压补偿 → 拆 PWM/方向 | 一般不用改 |
| `cpp/src/servo.cpp` | 舵机限速缓动（防 5V 塌陷导致单片机复位） | 一般不用改 |
| `cpp/src/arm.cpp` | 八个动作脚本 + 串行动作序列器 | ⚠️ **舵机角度标定完抄回这里** |
| `cpp/src/vision.cpp` | 14 字节定长帧解析 + 自动对位的 P 控制 | 一般不用改 |
| `cpp/src/hal_mcu.cpp` | 硬件抽象层的**真机实现**（碰寄存器） | 不用动 |
| `cpp/src/hal_sim.cpp` | 硬件抽象层的**模拟器实现**（写内存） | 不用动 |
| `cpp/main_mcu.cpp` | 真机入口 + 串口命令表 + 主循环调度 | 想加串口命令改这里 |
| `cpp/main_sim.cpp` | 离线自检用例（6 组断言） | 想加测试改这里 |
| `tools/build_cpp.py` | C++ 版构建脚本 | 敲命令 |
| `tools/sim/run_cpp_sim.py` | 模拟器驱动（读日志 + 判 PASS/FAIL） | 敲命令 |

**一句话概括你要动的**：`params.cpp`（参数）+ `arm.cpp`（角度）+ 敲两条命令。

## 五、C++ 版固件的串口命令

烧 `cpp/build/mcu/firmware.bin`，串口 PA9/PA10、115200，**发一个字符即可，不用回车**。

```
运动： w 前进  s 后退  a 左移  d 右移  q 左转  e 右转  x 停  z 斜走45°  r 自动演示
机构： 1 收起  2 待命  3 地面取块  4 台阶取块  5 入仓  6 挑物资架  7 洞窟  8 放铲
微调： [ ] 夹爪∓5°   - = 大臂∓5°   , . 前铲∓5°   m 打印当前角度
视觉： v 造一帧测试数据（不接摄像头也能验证）   V 打印视觉状态
其他： h 帮助   0 急停解除
```

**微调完的角度要抄回 `cpp/src/arm.cpp`**（或 C 版的 `config.h`），否则下次烧录又回默认值——这是新手最容易白干的一件事。

## 六、模拟器实测数据（ARM 机器码真跑出来的，不是我推算的）

```
[1] 麦轮解算
  纯前进   [+0.850 +0.850 +0.850 +0.850]   四轮同号同值 ✓
  纯左移   [-0.850 +0.850 +0.850 -0.850]   LF/RB 负、RF/LB 正 ✓
  斜走45°  [+0.000 +1.000 +1.000 +0.000]   ← 注意这个
  三轴全给 [-0.218 +1.000 +0.564 +0.218]   |w|max=1.000（归一化生效）

[2] 方向保持：反算角 vs 期望角，误差 0.000°（全部用例）

[3] 斜坡：0 → 95% 用 270ms（理论 283ms）；松手 → 停住 145ms

[4] 死区：speed 0.05 → duty 0.341；0.50 → 0.710；1.00 → 1.000

[5] 地面取块序列：耗时 3970ms，同一时刻最多 1 个舵机在动 ✓

[6] 视觉：好帧解析正确（含负数坐标）；坏校验被丢弃；垃圾数据后能重新对齐
```

**斜走 45° 那行值得单独解释**：四轮解算是 `[0, 1, 1, 0]`，即**只有右前和左后两个轮在转**。这不是 bug，是麦轮的固有特性——纯对角线移动时只有一条对角线上的两个轮出力，另外两个轮速度为 0。看到这个不要以为是代码错了。

**3970ms 一个取块动作偏慢**，5 分钟一局大约能取 20 多个。想加快有两个旋钮：把 `servoDps` 从 240 提到 360（前提是不烧舵机、不拉塌 5V），或者把 `arm.cpp` 里各步的 `waitMs` 调小。建议先只改 `waitMs`，风险小。

## 七、这套代码我验证了什么、没验证什么

**已验证（本机实测）**：

- ✅ C++ 真机固件编译链接通过，25.3KB Flash / 3.3KB RAM（芯片 64KB，余量充足）
- ✅ 模拟器里执行真实 ARM 机器码，6 组断言全 PASS
- ✅ 运动学方向、归一化、斜坡、死区、序列串行性、视觉帧解析

**没验证（要你上电实测）**：

- ❌ 舵机角度——这是按机构几何推的初值，你的装法不同，必须在线标定
- ❌ 真机跑起来的实际表现（打滑、跑偏、夹不夹得住）
- ❌ 视觉对真实 K210（我只验证了自己造的帧能被正确解析）
- ❌ PS2 手柄——C++ 版根本没接，打比赛用 C 版

**上电前三条**：① 车架空 ② 电池 ≥7.0V ③ DRV8833 的 nSLEEP 接高。舵机听到"吱吱"声立刻断电，那是超行程在硬撑。
