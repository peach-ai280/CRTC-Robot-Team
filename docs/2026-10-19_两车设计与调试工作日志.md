# CRTC 新生组备赛工作日志

整理日期：2026 年 10 月 19 日

这份日志记录两台车从需求确认、机械设计、打印，到程序编写和实车排查的进展。前面有些工作没有留下准确日期，按实际推进顺序整理，不补写日期。模型计算、电脑检查和实物测试分开记录。

目前机械方案已做到 V03，两台车采用相同结构，每台计划存放 10 块方块。麦轮遥控程序已交付，我已在另一台电脑完成烧录，但四个轮子仍没有转动。后面又出现手柄连不上的情况，调试暂时停在这里。

这里记录的是 V03 试装包和 `STM32_PS2_Delivery_20261019` 独立工程。仓库里还保留着早期模型和固件，尺寸、舵机配置、程序接口与本次交付有差别，使用时先确认版本。

## 一、先把两台车的要求定下来

参加新生组，两台车的底盘已经装好，机械臂和储物机构需要另做。最初的想法是先保证每台夹住一个方块，机构尽量简单，方便打印和装配。后来增加了储物要求：每台仓内放 10 块，装满后，机械臂还可以夹住另一块。

已确认的底盘数据如下：

| 项目 | 数据或要求 |
| --- | --- |
| 两车含轮外形 | 长 310 mm、宽 230 mm，两台相同 |
| 金属底板 | 310 × 149 mm |
| 安装平台离地高度 | 37.5 mm |
| 轮子直径 | 60 mm；前面说的“厚度 60”后来确认是直径 |
| 轮子安装位置宽度 | 102 mm；不能当作轮宽或轴距使用 |
| 收拢范围 | 新增机构收拢后不超出 310 × 230 mm |
| 抓取范围 | 工作时允许伸出底盘 |
| 初始打印条件 | 拓竹 A1 mini、PETG |
| 打印时间 | 最初希望单车不超过 6 小时，后来接受约 9 小时 |

底盘已有孔距、车轮实际宽度、部分板卡和电池盒外形还没有完整实测。模型中的安装位置有些是设计预留，装车时仍要核对。

查阅《2026CRTC参赛手册V1.5》后，发现初始尺寸上限为 290 × 195 × 210 mm，已有底盘的长、宽超过限制。我当时决定先保留底盘，按 310 × 230 mm 的范围继续设计。因此，当前方案不能记为已经满足比赛尺寸要求。整车重量、展开边界和赛道通过性也还没有完成实测。

## 二、机械方案从单块抓取改到十块存仓

前期保留了 V01 和 V02 文件。V02 以单块抓取为目标，已经有 STL、STEP、装配说明、姿态检查和 A1 mini 切片文件，单车切片估时约 9 小时。

V03 在此基础上加入十块料仓，并根据“少打印几种零件”的要求，把底座、支架和臂板尽量合并。两台车共用一套结构，先装好、调通一台，再做第二台。

机械臂方案是肩、肘使用 MG995，腕部和开爪使用 SG90。开爪舵机放在底盘，通过软管和拉线打开夹爪，弹簧负责闭合。单车方案需要 2 个 MG995、2 个 SG90；两台共需要 4 个 MG995、4 个 SG90，要与实际领用数量对照。

夹持对象按 30 × 30 × 30 mm 方块设计。夹指需要加软垫，接触方块外框，避开中间空孔。夹爪能否稳定夹住、断电是否掉块、机械臂是否下垂，均没有实物通过记录。

V03 的模型收拢外框为 310 × 230 × 185 mm，没有计入真实线束和天线。料仓内腔约 164 × 88 × 66 mm，计划沿车长放 5 块、分上下两层，共 10 块。十个存放位置及部分进出路径已做离散碰撞检查，检查范围内未发现模型相交，但没有验证实际落料、反弹和叠放是否稳定。

料仓文件名是 `24_front_hopper`，实际方案说明中采用后置低位安装，装配位置要按总装和说明核对，不能只看文件名判断。

减少零件种类并没有同时缩短总打印时间。V03 留存的 PETG 切片结果如下：

| 配置 | 单车估时 | 单车用料 |
| --- | --- | --- |

| 快速试打配置 | 14 小时 53 分 33 秒 | 358.06 g |

这些时间不含换盘、清理支撑、试片和失败重打。V03 仍超过后来接受的约 9 小时，需要继续减重或调整结构，不能算已经解决打印时间问题。

## 四、料仓改用 P2S 打印，以及首层失败

随后拿 `24_front_hopper.stl` 尝试在拓竹 P2S 上打印，期间反馈过文件不兼容。现有目录中保存了 `24_front_hopper_P2S_导入后切片.3mf`。

整理时检查了这个 3MF：里面只有模型数据，没有 P2S 打印机配置、耗材配置或已切片 G-code。因此它是供导入的模型文件，需要在 Bambu Studio 选择实际的 P2S、喷嘴和耗材后重新切片，不能把原 A1 mini 的切片直接当作 P2S 打印任务。

这次料仓的耗材改为 PLA，我也明确过材料变更只针对这个件，不代表整套承力件都改成 PLA。旧的 PETG 切片参数不能直接沿用。

实打时一开始就出现“炒面”，进一步确认是首层粘不牢，并发了首层照片。其他模型能正常打印，这说明要重点检查这个料仓的摆放、底面接触和切片设置，但还不能据此认定模型有缺陷。

目前没有记录到一次成功的料仓复打，也没有足够证据确定唯一原因。后续复打需要核对实际底面是否贴板、首层预览有没有悬空区域、支撑是否正确，以及 PLA、热床板型和首层参数是否匹配；同时检查打印板清洁和调平情况。

## 五、半自动存仓要怎么操作

希望的操作方式已经说清楚：人遥控小车夹起方块、停稳，再按一个确认键，由机械臂把方块放进料仓。暂时不要求机器自己判断是否满仓。

已有存仓流程说明：

1. 按当前计数选择储位，先放底层 5 个位置，再放上层 5 个位置。
2. 机械臂到储位上方，下降、开爪、退出，再回到携带姿态。
3. 完成后计数加一，计数为 10 时停止继续入仓。
4. 清空料仓后人工复位计数，漏放或卡住时也需要人工修正。

目前做到的是模型储位、动作路径和状态流程，尚未合并进本次麦轮遥控固件。舵机中心、转动方向、限位、角度与脉宽对应关系、确认键都还需要实车标定。按次数计数也不能证明每块都确实落进仓里。

另外曾提出“按 PS2 一个键，舵机转到 135°并保持 5 秒”的小功能，后来决定本次先不加入。当前交付程序不含舵机、机械臂或自动存仓控制。

## 六、2026 年 10 月 19 日：重新编写麦轮遥控程序

一开始提供的是 `interface_baseline.json`。检查后确认它只是接口配置，不是能直接检查、编译的完整工程。随后决定重新编写 STM32 程序，使用 PS2 手柄控制四个麦轮，交给另一台电脑编译并用 ST-Link 烧录。

硬件选择参考手册物资表：STM32F103C8T6、DRV8833 双路驱动模块、PS2 无线手柄。照片里的“V318”只是板上标识，不能据此确认实际驱动芯片。程序按 DRV8833 编写，实物型号仍需核对。

正式源码和电脑检查文件已经分开存放：

- `01_Firmware`：正式源码、Keil 工程、链接脚本和中文说明。
- `02_PC_Checks`：电脑测试源码、测试程序和日志，不加入烧录工程。
- `STM32F103C8_PS2_Firmware.zip`：只打包正式工程，供另一台电脑使用。

正式工程包含 `main.c`、`board.c`、`ps2_bus.c`、`robot_control.c`、`driver_encode.c`、`startup.c` 六个 C 文件，使用 Keil MDK 和 ARM Compiler 6。

当前引脚记录如下，左右前后均按车辆前进方向定义：

| 功能 | STM32 引脚 |
| --- | --- |
| PS2 CS / ATT | PB0 |
| PS2 CLK | PA5 |
| PS2 DAT / DO，接收器输出 | PA6 |
| PS2 CMD / DI，主控输出 | PA7 |
| 左前电机 IN1 / IN2 | PB6 / PB12 |
| 右前电机 IN1 / IN2 | PB7 / PB13 |
| 左后电机 IN1 / IN2 | PB8 / PB14 |
| 右后电机 IN1 / IN2 | PB9 / PB15 |
| 状态灯 | PC13，按低电平点亮处理 |
| SWDIO / SWCLK | PA13 / PA14 |

PS2 的 CS 和电机引脚保留接口配置，PS2 另外三根线沿用旧工程记录，仍要与实物接线对照。四路 PWM 使用 TIM4，频率 10 kHz。默认正常输出上限为 35%，慢速为 18%，四个电机的方向修正值暂时都是 `+1`，装车后需要架空核对。

默认操作：

| 操作 | 功能 |
| --- | --- |
| 摇杆回中、松开 L1，再新按 START | 启用行驶 |
| 持续按住 L1 | 允许电机运动 |
| 左摇杆或方向键 | 前后、左右平移 |
| 右摇杆左右 | 车身转向 |
| 按住 L2 | 慢速 |
| 松开 L1 | 输出归零 |
| SELECT | 锁定停车，回中松 L1 后再按 START 解除 |

程序有 100 ms 有效帧超时停车和约 0.5 s 看门狗。输出归零采用滑行，不能当作机械抱死。部分无线接收器失联后可能继续重复旧数据，因此仍需要实测关闭手柄后的停车行为。

电脑检查通过了 793,678 项断言，覆盖手柄数据解析、麦轮混合、启停、超时、换向和 DRV8833 输出编码等。六个正式 C 文件通过电脑 GCC 语法检查，工程路径、启动文件分支和中断向量表也做了检查。这些检查不等于 ARM 目标编译或实车验证。

源码交付时只做了上述电脑检查，没有附上 ARM 目标构建结果。之后我在另一台电脑完成编译、烧录，并反馈烧录成功；当时没有留存编译日志。

## 七、烧录后四轮不动，开始查供电和通信

下面按实际反馈记录，未确认的地方不下结论：

| 顺序 | 现象或操作 | 当时能确认的内容 |
| --- | --- | --- |
| 1 | 烧录后车不动，主控黄灯闪、红灯常亮 | 主控有上电表现，但不能说明驱动电源正常 |
| 2 | 回中、松 L1、按 START，再按住 L1＋方向键上 | 四轮完全没有反应 |
| 3 | 按 START 后黄灯常亮 | 程序至少能识别启用指令 |
| 4 | 按 SELECT 后黄灯闪烁 | 软件停车状态能切换 |
| 5 | 测到过 0.7 V | 后来确认测量位置不清楚，这个数不能当作驱动 VM 电压 |
| 6 | 电池输出测得 7.8 V | 只确认电池端电压，还不能证明已送到驱动板 |
| 7 | 看整车接线照片，确认蓝色继电器控制电机电源 | 继电器在电机供电路径中 |
| 8 | 确认继电器由独立小遥控器或按钮控制 | 不需要由 STM32 增加 IN 控制程序 |
| 9 | 用独立遥控器接通后，再按 START、L1＋方向键上 | 四轮仍完全不动，故障未解决 |
| 10 | 随后手柄与接收器连不上 | 新增通信问题，尚未恢复并验证 |

照片中接线较密，端子文字不够清楚，不能逐根确认供电、共地、驱动输入和输出是否正确。继电器有动作或指示灯亮，也不能证明输出端电压已经正常送到驱动板。

接下来的排查应先恢复手柄通信，再确认驱动板 VM 对 GND 的实际电压，以及 nSLEEP、PWM 和共地。此前未得到可靠的驱动输入电压，也没有拿到 Keil Watch 的实时数据，因此不能直接归因为代码或某一块硬件损坏。

可在 Watch 中看 `g_debug.connected`、`g_debug.armed`、`g_debug.emergency`、`g_debug.wheel[0..3]` 和 `g_robot.latest.buttons`。这能区分“程序没有给运动指令”和“已有指令但电机未响应”。暂停或单步时默认看门狗可能复位，调试配置要另外处理，结束后恢复正常设置。

关于后来手柄连不上，手册只确认使用可对频锁定款，没有给出这块接收器的具体按键步骤。目前没有确认其指示灯状态、供电测量结果或专用对码方式，不能把通用配对方法写成这套设备已验证的操作。
