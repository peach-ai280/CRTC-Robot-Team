## 一、规则拆解与战术选型

### 功能描述

比赛一局 5 分钟，两台车要在场地里收集能量单元（白色，1 分）和能量核心（黄色，4 分）。
半自动有 1.5 倍率，全自动有 2 倍率。我们要在"能稳定拿到的分"和"冒险搏高分"之间做选择。

### 开发历程

**先把分算清楚，再决定怎么打。** 我们做的第一件事不是画图，而是把得分规则列成表，
算出几种打法的**理论得分上限**：

- 18 个白块散布在地面上，单个 1 分；
- 5 个黄块，单个 4 分，位置都很刁钻（中央高台、物资架 250mm 高、洞窟里、焦点平台）；
- 倍率：全自动 ×2、半自动 ×1.5、手动 ×1。

**核心决策：不赌全自动，先把半自动做稳。**
全自动要处理"方块被对手推走了""地面脏了打滑了"这些现场变化，我们几个都是新生，
写不出可靠的现场判断逻辑。半自动只要把"对中 + 一键宏"做扎实，1.5 倍率是拿到手的。

**走桥，不爬坡。** 场地中央高台（300mm）有一条桥（f5/g5），红方 1 号机的启动区
本身就是高台，走桥上去抢中央的黄色能量核心，性价比最高。
另一条路是爬 26.6° 的坡道，但麦轮在那种坡度上辊子会打滑 —— **我们判断收益期望是负的，果断放弃。**

> 详细版见 `docs/01_规则拆解与战术选型.md`。

## 二、机械结构与 3D 打印件设计

### 功能描述

设计车架：在规则尺寸内（初始 ≤290×195×210mm、重量 ≤2.0kg），把底盘、电控、储仓、
机械臂装进去，并且要能扛住 180mm 自由跌落不掉件。

### 开发历程

**先算红线，再画零件。** 我们没有一上来就建模，而是先把规则尺寸摊开算：

| 限制 | 我们的设计 |
|---|---|
| 长 ≤ 290mm | **283mm**（金属底板 255 + 收集铲前伸 28）—— 只剩 7mm，最紧的一条 |
| 宽 ≤ 195mm | 162mm |
| 高（检录姿态）≤ 210mm | 148mm |
| 重量 ≤ 2.0kg | 逐项累加 ≈ 1076g，余量还很大 |

**铲子为什么从 90mm 砍到 28mm**：一开始设计的收集铲前伸 90mm，一算整车长 345mm，
**直接违规**。砍到 28mm 之后整车 283mm。但铲子短了方块会滑进车底 ——
所以必须在车尾加一块后壁挡板（`05d`），这是配套改动。

**参数化建模，不手工画图。** 我们写了脚本 `mechanical/gen_parts.py`，改一个尺寸就重跑生成 STL，
不用在 CAD 里一个个零件改。好处是"改铲子长度"这件事只改一行参数，顺便能立刻算出整车尺寸有没有超。

**尺寸是怎么算的、不是怎么量的**：上面表里的数字**全部是设计值**。
这里面还有一条要特别当心 —— 上面那套"高度栈"（板面离地高度）取决于实测的**轮外径**
（Φ60 / Φ50 / Φ40 三种轮子对应三种垫高方案），**装上真轮子量完才能定**。

> ⚠ **当前状态：模型和 STL 生成完了（25 个结构件 + 14 个外观件），一件都还没打印。**
> 详细的结构说明、重量核算表见 `docs/02_机械结构与3D打印.md`。

## 三、底盘全向运动与麦轮防滑

### 功能描述

用四个麦克纳姆轮实现全向移动：前后、左右平移、原地自转，而且**平移时车不能自己偏航**。

### 开发历程

**第一步：纸上推运动学。** 麦轮的特点是辊子斜 45°，四个轮的转速组合能合成任意方向的速度。
我们用 X 型布局，先手推了逆解公式：给定"前进速度 vx、横移速度 vy、自转 wz"，
算出四个轮各自该转多快。

**第二步：踩到最经典的一个坑 —— 横移时车自己转圈。**
原因是我们对四个轮分别做了"超过 1 就截断到 1"的限幅。当某个方向合成的速度很大时，
有的轮被截断、有的没被截断，四个轮的**相对比例就被破坏了** → 车斜着跑。

**解法：整体等比归一化限幅。** 不逐轮截断，改成先找出四轮里绝对值最大的那个，
如果它超过 1，就把**四个轮同时**除以这个最大值。这样比例永远不变，
只是整体"降速"，方向绝不会偏。

> 这是我们这个周期**最重要的一次改动**。方向一偏，后面的对中、携带全都白做。

**第三步：防滑四件套。** 麦轮在光滑地面上起步容易打滑，我们叠了四层保护：

| 措施 | 解决什么 |
|---|---|
| 加速度斜坡（加速和减速分开设） | 起步不要一脚踩到底，避免轮子空转 |
| 死区补偿（油门小于 0.18 当 0） | 摇杆回中不准导致车"自己爬" |
| 起步助力（kick） | 死区以上第一下给个短促大电流，克服静摩擦 |
| 高速限自转 | 速度越高，自转上限越低，防止甩尾 |

**为什么不做编码器闭环**：编码器要额外买、要装、要标定，我们的时间不够。
开环 + 参数调好，对"收集方块"这个精度要求是够的。**代码里留了接口，以后想加随时能加。**

> 详细推导、调参对照表见 `docs/03_底盘运动与麦轮防滑.md` 和 `docs/调参指南.md`。

## 四、电源、驱动与接线

### 功能描述

把 7.4V 电池的电安全地分给电机、舵机和单片机，并且满足规则"只能有一个供电模块"。

### 开发历程

**先读规则再接线。** 手册规定：每台车只允许 1 个供电模块，额定电压不超过 7.4V，
而且**必须能适配官方的无线继电器**（10m 内遥控断电，检录要测）。
所以电源树是这样设计的：

```
2×18650 串联（7.4V）→ 无线继电器 → 节点P ─┬─→ DRV8833 ×2 的 VM（电机直供）
                                          └─→ 5V 降压 → STM32 + 舵机
```

**第一个坑：继电器要从电池直出处取电。** 如果把继电器的 `IN+/IN-` 接到降压之后的 5V 上，
遥控断电后继电器自己也没电了，就**永久断不回来**。必须接在电池直出的那一段。

**第二个坑：红色 DRV8833 模块的 VCC 和 VM 是短接的。**
这类模块常常用一个 0Ω 电阻把逻辑电源 VCC 直接连到电机电源 VM，
而 VM 上挂的是 8.4V 满电电压，**超过 VCC 的 7V 上限**。
解法是切断那个 0Ω 电阻（或铜箔），VCC 单独飞线到 5V。

**第三个坑：DRV8833 的 nSLEEP 悬空 = 电机完全不转。**
这是最常见的"以为驱动坏了"。nSLEEP 必须拉到高电平（接 VCC），否则芯片处于休眠。

**第四个坑（也是新手最容易吃的）：舵机一动，单片机就复位。**
MG995 大臂舵机堵转电流能到 1.5A，而 5V 降压同时还在喂 STM32，
舵机一用力就把 5V 拉塌 → 单片机欠压复位。解法是给舵机单独一路降压，
并在 5V 主干上并一颗 470µF 电解电容 + 0.1µF 瓷片电容吸收瞬时冲击。

> ⚠ **当前状态：电源树方案定了、接线表出了，但还没实际接线通电。**
> 完整引脚表、焊接点位、分步上电检查清单见 `docs/硬件接线与焊接指南.md`。

## 五、PS2 手柄遥控与通信

### 功能描述

用官方的 PS2 无线手柄控制机器人，并且**手柄一掉线，车必须立刻停下来**。
这是安全要求，不是可选功能。

### 开发历程

**协议本身：SPI 模式 3。** PS2 手柄的 SPI 时序是"空闲时钟高、第二个边沿采样"。
我们用的参数：CPOL=High、CPHA=2Edge、分频 256（约 281kHz）。
**为什么不更快**：便宜手柄在 500kHz 下会偶发丢帧。轮询一帧只要 0.26ms，
在 5ms 控制周期里占 5%，**慢一点换来不丢帧，值得**。

**最折磨人的一个坑：DI / DO 接反，查了三个小时。**
现象是串口一直没有任何按键数据。我们依次排除了：量接收器电压（正常）、换手柄（一样）、
把 SPI 四种模式组合全试一遍（一样）。
最后用示波器看波形才发现 —— **MISO 上一直是高电平**，说明我们的数据线接到了手柄的"数据输入"脚上。

根源是接收器的丝印是**站在手柄角度**命名的：

| 丝印 | 含义 | 接 STM32 |
|---|---|---|
| DI | Data In（进手柄） | MOSI（PA7） |
| DO | Data Out（出手柄） | MISO（PA6） |

我们是站在单片机角度接的，正好反了。
**教训写进代码注释了：PS2 连不上，先对调 PA6/PA7 —— 十次有九次是这个原因。**

**进模拟量模式。** 手柄上电默认是数字模式，摇杆只有 0 和 255 两档，没法做速度控制。
必须在初始化时进配置模式打开模拟量。**注意配置命令之间要有延时** ——
我们第一版没加延时，配置命令全被吞了。

**掉线保护（这条是安全底线）。** 掉线时不能只是"不再更新指令" ——
那样车里会保留最后一次的速度，**一直跑下去直到撞墙**。必须显式清零：

```c
if (!PS2_Poll()) {
    lost_cnt++;
    if (lost_cnt > 25) {          // 约 125ms
        connected = 0;
        btn = 0;
        lx = ly = rx = ry = 0;    // 关键：清掉残留摇杆量
    }
}
```

**没有串口怎么看状态**：我们给板载 LED 写了一套状态机 ——
常亮=通了、每秒闪 2 下=数据线接反、每秒闪 1 下=对面没回应、每秒闪 1 下双闪=数字模式需重启。

> ⚠ **当前状态：这是目前唯一在推进的一环。**
> SWD 烧录链已经实测打通（`flash.py check` 返回 `Device ID 0x410`、电压 3.21V），
> 正在接 PS2 那 6 根线做桌面测试。**还没跑到"摇杆能控车"这一步。**
> 接线表、LED 判读、协议细节见 `docs/05_PS2手柄与遥控器.md`。

## 六、舵机机构与抓取

### 功能描述

一台车要能：夹起方块、挑下物资架上的黄块、伸进洞窟够方块。
用 1 个大舵机（MG995，管大臂）+ 3 个小舵机（SG90，管夹爪 / 前铲 / 备用）。

### 开发历程

**52 和 46.4 这两个数**：方块对角线是 42.4mm，喉口必须比它大，我们取 46.4mm；
而**夹爪闭合后的净距必须小于 30mm**（方块边长），否则夹不住。一开一合之间就是夹爪的行程。

**为什么要给舵机做缓动。** 舵机直接收到一个角度跳变，会以最大扭矩瞬间转过去 ——
结构上冲击很大，塑料件容易裂。所以给舵机做了限速（每秒 240°），动作更平滑。

**"舵机运动（多项）"这个考核点。**
手册要求"同一台车至少 3 个舵机同时动，且能在**任意非初始状态下保持相对静止**"。
后半句是关键：不能只是会动，还要**扛得住力、停在中间角度不动**。
所以我们给夹爪加了"保持力矩"状态（`SERVO_GRIP_HOLD_CUBE`），
并且这需要一台车上真的挂 3 个舵机 —— **这就牵出一个采购问题：官方每车只给 2 个 SG90，
要拍这一项得凑够 3 个**（我们的方案是两台车的舵机集中到一台车上拍）。

**给不动的那个舵机留了备用位。** PA3 那一路默认不装，留着以后加机构。

> ⚠ **当前状态：舵机驱动代码写完了，但机构一个都没装（打印件还没打）。
> 夹爪角度、大臂高度全部是设计值，必须上车标定。**
> 见 `docs/06_舵机机构与抓取.md`。

## 七、方块携带与储仓

### 功能描述

让机器人能"拿住"方块并且**不掉**——判定标准是：物体与机体接触，且在重力下
沿**任意方向（包括上下）**都能跟着走。

### 开发历程

**先把"携带"的判定抠准。** 规则原文说"能跟着走就算携带"，所以关键是"不掉"。

**设计：斜槽 + 单向挡板。** 储仓底部做成 5° 前低后高，方块靠重力自己往里滚；
入口装一个单向挡板，进去的时候被推开，想出来的时候被挡住。
**急停、横移、跌落的时候都不掉** —— 这就是我们把储仓做成"越晃越稳"的思路。

**储仓做几格**：规则按"结束时车上还剩几个道具"算分，所以仓越大分越高。
我们算下来储仓内腔做成 126×110mm，能放 4 列 × 3 排 = 12 个的位置（实际常用 3 格，够用就行）。

**备用方案**：如果储仓容量不够，车顶可以"粘"一块（用魔术贴），
但这是兜底，不是主方案。

> ⚠ **当前状态：只有设计，没打印、没装配，**掉不掉**还得等真车才知道。**
> 见 `docs/07_方块携带与储仓.md`。

## 八、半自动对中与一键宏

### 功能描述

车自己走到方块旁边、对准、把方块收进来 —— 操作手只要按一个键，不用精细操作。
这样能拿 1.5 倍率。

### 开发历程

**最重要的一次技术选型：机械对中 vs 视觉识别。**

| | 机械对中（我们的选择） | 视觉识别（K210） |
|---|---|---|
| 靠什么 | V 型口 + 双微动开关 | 摄像头找色块 |
| 失败模式 | 没对准（无害，重来一次） | **对准了错的目标（有害，浪费时间还可能撞车）** |
| 成本 | 两个微动开关 ¥8 | 模块约 ¥90 |
| 调试 | 简单 | 光照一变就要重抠阈值 |

**我们选机械对中。** 不是因为它更先进，而是因为它的**失败方式更安全**。
视觉的失败是"自信地做错事"，对新手队来说风险太高。视觉代码我们也写了，
放在 `vision/` 里当**进阶备选**，不押它。

**一键宏怎么保证安全。** 宏是"基于时间参数的盲走"，一旦现场和标定时不一样
（方块被对手推走了、地面脏了），继续跑会把车顶在墙上。所以：

- 总时长 240s 上限；
- 连续失败 3 次就放弃；
- **操作手一动摇杆（三轴绝对值之和 > 0.35），宏立刻中止、交还控制权**。

最后一条是"这个宏敢上场"的唯一原因。

**三档模式**：手动 / 半自动 / 全自动，用 PS2 的 SELECT 键循环切换。
全自动其实是"半自动宏的自动调度器"，不重写抓取动作 ——
**所以我们的路线是：先把半自动调稳，再上全自动。**

> ⚠ **当前状态：代码写完、离线仿真跑过，未上真车。**
> 怎么切模式、五个宏分别是什么、参数怎么标，见 `docs/半自动与全自动操作手册.md` 和 `docs/08_半自动与视觉.md`。

## 九、结构稳定性、尺寸与成本

### 功能描述

拿三条"不过就完蛋"的硬指标立账：180mm 跌落无零件掉出、尺寸在规则内、成本可控。

### 开发历程

**跌落**：手册要求从 150~200mm 处底面朝下自由落体，无零件掉出。我们按最严的 **180mm** 准备。
预判的风险点是夹爪指只用一颗 M2.5 螺丝固定，落地冲击可能把 PLA 的螺丝孔扩孔。
对策是：螺丝孔改成穿通孔 + 螺母、夹爪指填充率提到 45%、舵机和转接板之间垫一层双面胶吸冲击。

**顺手发现一个反常识的点**：**电池是全场最容易掉的东西**。
两节 18650 加盒子约 100g，落地冲击很大。我们用卡箍 + 一根扎带双重固定，
而且把卡箍装在甲板**下方**（顺便降低重心）。

**尺寸**：长 283mm 只比 290 的红线少 7mm，装完保险杠和铲之后**必须再量一次**。

**成本**：手册规定 3D 打印件只按**原料价格**计入成本（不是按你实际掏的钱）。
所以一卷 PLA 我们只用 1/4，就只算 ¥15。规则还有一条：

## 十、工程环境与工具链

### 功能描述

搭一套能稳定"改代码 → 编译 → 烧进板子"的工作环境，并且让代码能被离线验证。

### 开发历程

**不用图形界面，全部脚本化。** 本机装了 STM32CubeIDE 2.2.0（提供 ARM 编译器和烧录器），
但我们**不进它的图形界面建工程**，而是自己写了两个脚本：

- `tools/build.py` —— 一条命令编译出固件（本机没装 make，所以自己写构建脚本）；
- `tools/flash.py` —— 一条命令烧录，并自动找到 CubeIDE 自带的烧录器。

**为什么自己写 HAL 兼容层。** 标准做法是用 ST 官方的 HAL 库 + CMSIS，但我们这套环境拿不到。
于是我们用**直接操作寄存器**的方式，自己实现了业务代码用到的 20 来个 HAL 函数，
**函数名和官方一模一样** —— 这样业务代码一个字不用改，将来拿到官方库也能一键切回去。
（详见 `docs/开源项目说明.md`）

**离线验证：在电脑上跑真实固件。** 我们用 ARM 模拟器（unicorn）在电脑上模拟一颗
Cortex-M3，直接把编译出来的**真实固件机器码**跑起来，看电机和舵机的输出对不对。
这样改一个参数不用每次都烧板子试。

**实测结果**：`flash.py check` 返回
`Device ID 0x410`、`NVM size 128 KBytes`、`Voltage 3.21V` ——
**"电脑 → ST-LINK → SWD → 芯片"整条路是通的。**
