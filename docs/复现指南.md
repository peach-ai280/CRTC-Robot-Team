## 一、先想清楚三件事

**第一，先把最短链路跑通，再加功能。** 顺序是：灯亮 → 一个轮子转 → 四个轮子转 → 听遥控 → 舵机 → 综合动作。每一步都要有一个能单独验证的完成标志，没达到就不要进下一步。我们中间有一次跳步，四个轮子还没单独验完就去调麦轮解算，结果车走歪了，分不清是算法错还是有一个轮子接反，白花一个下午。

**第二，代码和硬件要能分开证明。** 车不动，可能是程序没跑，也可能是线没接对、模块坏了。这两件事必须能分头查。办法是留一个「不依赖硬件也能看见状态」的出口——板载 LED，或者串口。我们后来靠读寄存器的值（`TIM4->CCR1` 是多少、方向脚 `GPIOB->ODR` 是什么）来证明程序确实在按预期输出，那时候才发现问题根本不在代码上。

**第三，早点拍照、早点录像。** 中期要交视频，赛后要写记录。你在现场觉得「这个不用记，我记得住」，三天后就记不住了。我们最后能拿出来的三段录像，都是当时随手拍的，正经想补拍的时候车已经拆了。

## 三、环境与烧录

### 编译

仓库里有三套构建脚本，都在 `tools/`：

```
tools/build.py       编 firmware/（功能最全的那套，含机械臂、半自动宏）
tools/build_v2.py    编 firmware_v2/（实车烧的就是这套）
tools/build_cpp.py   编 cpp/（能在电脑上离线跑，不烧板子）
```

`firmware_v2` 有四个开关，能编出四种用途不同的固件：

```bash
python tools/build_v2.py              # 默认：PS2 遥控整车控制
python tools/build_v2.py --selftest   # 四轮依次单独转，用来查轮位和方向
python tools/build_v2.py --demo       # 自动演示：前进后退平移自转 + 舵机
python tools/build_v2.py --servo      # 打开舵机通道
python tools/build_v2.py --car2       # 车二的电机极性（和车一不同，别烧错）
```

建议第一次上手先编 `--selftest`，它不依赖手柄，上电就自己转，最适合验证「板子活着、电机动了」。

### 烧录

这是全程最花时间的一关，先说结论：**我们那块 ST-LINK 是克隆版 V2，固件 `V2J29S7`，ST 官方的 CubeProgrammer 完全握不上手**，一律报 `DEV_CONNECT_ERR`，日志里 FW 字段是空白的。当时差点当成线接错了，白拆了半天。

能用的是 OpenOCD，而且要指定 `interface/stlink-dap.cfg`：

```bash
openocd -f interface/stlink-dap.cfg -f target/stm32f1x.cfg \
        -c "adapter speed 300" \
        -c "program firmware_v2/build/firmware.bin 0x08000000 verify reset exit"
```

用 `stlink.cfg` 会报 `Infinite eval recursion`，别在这上面浪费时间。如果 openocd 报找不到 cfg 文件，加 `-s` 指向 CubeIDE 里那份脚本目录（`plugins/.../resources/openocd/st_scripts`）。

第二个坑是 **SWD 四根线的顺序**。Blue Pill 板上那排小针是 `3V3 / SWIO / SWCLK / GND`，ST-LINK 那头的右列是 `SWCLK / SWDIO / GND / 3.3V`——**顺序是反的**。整排杜邦头直接怼上去，等于把 3.3V 接到 GND 上。必须四根独立线按丝印对插。我们把 SWIO 和 SWCLK 插反过一次，症状是 `init mode failed`，但 ST-LINK 本身能被电脑认到、能读出 3.27V，很容易误导你以为线没问题。

我们的 `tools/flash.py` 把上面这些封起来了。注意它烧的是哪个文件——两套固件的产物不在同一个目录：

```bash
python tools/flash.py check     # 只连板上、读芯片 ID，不动 flash。第一次先跑这个

# firmware_v2（实车这套，纯寄存器无 HAL）
python tools/flash.py v2        # → firmware_v2/build/firmware.bin
python tools/flash.py v2s       # → firmware_v2/build/firmware_servo.bin（车一，带舵机，我们烧的就是这个）
python tools/flash.py v2c       # → firmware_v2/build/firmware_car2.bin（车二）
python tools/flash.py v2cs      # → 车二 + 舵机

# firmware（功能最全那套，含机械臂和半自动宏）
python tools/flash.py motion    # 底盘测试固件
python tools/flash.py ps2       # PS2 测试（不初始化电机舵机，车不会动）
python tools/flash.py arm       # 机构测试
python tools/flash.py full      # 完整版
```

`build_v2.py --demo` 编出来的 `firmware_demo_servo.bin` **不在 flash.py 的映射表里**，得手敲上面那条 openocd 命令。这个我们当时没补进去，用的时候注意一下。

### 上电之前

板子通电前有五件事要核，写在 [硬件接线与焊接指南](硬件接线与焊接指南.md) 里。其中最重要的一条：**四轮同时堵转的电流是 4.8~6 A**，而电池盒的弹簧片大约只能过 2 A，26AWG 杜邦线大约 1 A。台架调试够用，真要上场，VM 那一段必须换粗线，接插件也要换。

## 四、接线

接线图和三路主干的总表在 [硬件接线与焊接指南](硬件接线与焊接指南.md)，这里只说最容易错的几处。

**电源走三条主干，不是一条。** 7.4 V 主干（电池正极 → 继电器 `NO` → 两块 DRV8833 的 `VM`）；5 V 主干（降压模块 `OUT+` → 单片机 5V 脚、接收器）；地主干（电池负极、继电器 `-V`、降压 `IN−`、两块 DRV 的 `GND` 全部连在一起）。

`IN−` 和 `OUT−` **不用你自己再焊一起**——非隔离 DC-DC 内部本来就是共地的，焊了不坏事，但不要以为漏了这一步就会不工作。

**降压模块的四个焊盘分别是 `IN+` `IN−` `OUT+` `OUT−`。** `IN+` 接继电器的 `NO`（不是 `COM`）。接 `COM` 的后果是降压模块在开关之前，遥控一断单片机还亮着，检录不合格。这个我们错过一次。

**DRV8833 只需要接 `VM` 和 `STBY`，不用找 `VCC`。** 红色那块板上没有 `VCC` 引脚。`STBY` 必须拉 5 V，不然芯片是睡着的，PWM 进去没反应。

**地线不要都焊在降压模块的细焊盘上。** 电机的大电流会从那里过，焊盘撑不住。电气上是同一个点，物理上要焊在 DRV 的 `GND` 或地主干上。

## 五、让一个轮子转

### 硬件

四个 TT 马达接两片 DRV8833，每片管两个轮子。信号侧这样接：

| 轮 | PWM（接 DRV 的 IN1） | 方向（接 DRV 的 IN2） |
|---|---|---|
| 左前 LF | PB6 / TIM4_CH1 | PB12 |
| 右前 RF | PB7 / TIM4_CH2 | PB13 |
| 左后 LB | PB8 / TIM4_CH3 | PB14 |
| 右后 RB | PB9 / TIM4_CH4 | PB15 |

PWM 10 kHz（`PSC=0`、`ARR=6399`），占空比 0~1000 对应 `CCR = 占空比 × 6.4`。

### 软件

`firmware_v2` 里干这件事的是 [driver_encode.c](../firmware_v2/src/driver_encode.c)（老那套 `firmware/` 里对应的是 `motor.c`）。有两处是**反直觉的，改之前先看懂**：

**一、反转要写成 `cmp = 100 - 占空比`。** DRV8833 在 IN/IN 模式下，两个输入脚是 `00` 滑行 / `10` 正转 / `01` 反转 / `11` 刹车。它是靠**低电平那一路**驱动反转的，所以占空比要取反写。我们当初看这段代码以为写错了，差点改掉，实际上它是对的。

**二、PWM 必须每个周期都重新写。** 寄存器会保持上次的值，你只调一次，它就一直是那个值。我们的起步助力（+0.12）当初只写了一次，结果这个助力永久冻住了，实测 `CCR` 一直是 3045 不动，车一给指令就往前窜。

老那套 `firmware/Core/Src/motor.c` 里还有个 `Motor_BrakeAll()`，原来是「方向拉高 + PWM 给 100%」。方向线一松，DRV 内部下拉变成 `10`，等于**全速正转**——而这个函数正好是 START 急停调的，按急停反而会冲出去。现在改成跟随 `MOTOR_IDLE_BRAKE`，默认滑行。这种「函数名和实际行为对不上」的地方最容易出事，动急停逻辑之前一定要读一遍它到底写了什么。

### 验证

编 `--selftest`，四个轮子会依次各转 4 秒，中间停 1.5 秒。看三件事：

1. 是哪个轮子在转（转的时候你手碰一下就知道）
2. 转的方向对不对（朝前还是朝后）
3. 五个轮位是不是都转到过

我们第一次跑这个，前两个轮子不转但能听见嗡嗡声。这个现象的意思是：DRV 芯片醒着（`STBY` 有 5 V），听得见 PWM，H 桥在试着驱动，但扭矩接近零。**原因是那块 DRV 的 `VM` 没接**，量出来只有 1.0 几伏——万用表在悬空的节点上会读出虚电压，10 MΩ 的输入阻抗足以让它显示一个看起来像样的数。VM 接到 7.4 V 主干之后就好了。

## 六、让车听懂遥控

PS2 接收器走 SPI1：`SCK=PA5`、`MISO=PA6`、`MOSI=PA7`、片选 `CS=PB0`（软件片选），SPI 模式 3，281 kHz。

**这三个地方错了就通不了：**

1. **`DI` 接 `PA7`，`DO` 接 `PA6`。** 接反了是 90% 连不上的原因。方向要按「从接收器看」来判断。
2. **`VCC` 是 3.3 V，不是 5 V。** 5 V 会烧接收器。
3. **接收器不能直接插到单片机上**，中间要过那块转接板。

回帧是 9 个字节，布局有点反直觉：`[1]` 是模式（41 = 数字、73 = 模拟绿灯、79 = 模拟红灯），`[2]` 固定是 `5A`，`[3][4]` 是按键，**`[5][6]` 是右摇杆、`[7][8]` 是左摇杆**。我们按常识以为左在前，找了两小时。

**绿灯亮不等于通了。** 绿灯只说明「手柄 ⇢ 接收器」这一段好，「接收器 ⇢ 单片机」是另一段，得看 `ps2.raw[9]` 是不是全 `FF`——全 `FF` 就是单片机根本没收到回应。

排障靠板载 LED（PC13，低电平亮）：

| LED 表现 | 意思 |
|---|---|
| 常亮 | 通了 |
| 每秒闪 2 下 | PA6 / PA7 接反 |
| 闪 1 下 | 接收器没回应 |
| 连闪两下 | 手柄在数字模式，要断电重插 |

`PS2_Init` 里那句 `memset(ps2.raw, 0xFF, 9)` 不能删。删了之后「没回应」和「收到全零」分不开。

**掉线必须停。** 遥控一关或者信号断了，杆量要立刻归零，不能让车带着上一次的指令继续跑。

## 七、舵机

舵机接 `PA3`（`TIM2_CH4`），50 Hz，脉宽 1000~2000 µs 对应两头，1500 µs 是中位。定时器配 `PSC=63`、`ARR=19999`，数出来正好 1 MHz 计数、50 Hz。

`firmware_v2/src/servo_lift.h` 里管着一个渐变的速率（`BOARD_SERVO_RATE_US_S = 400`），不让舵机瞬间蹦到目标角度——瞬间到位会撞机构、也会拉低电压。

**先标定，再装机构。** 让舵机空着走完全程，记下两个极限到哪儿，再把夹爪装上去。我们是先装后标的，结果最低档爪尖直接穿进甲板，最后靠固件互锁才挡住。

**检录姿态**：舵机转到 90°（爪朝车侧），升降停在最高档。这个姿势是为了收进初始尺寸的框里。

## 八、上车联调

顺序照抄：

1. 四轮架空，看每个轮子方向对不对（`--selftest`）
2. 落地，前进后退走直线
3. 单独测平移
4. 单独测原地转
5. 接遥控，重复 2~4
6. 加舵机，单独走一遍行程
7. 综合动作

`--demo` 编出来的固件就是第 7 步：15 段、24 秒，前进后退各 3 秒、左右平移各 2.5 秒、左右自转各 2.5 秒，段间停 0.6 秒，然后舵机 1500 → 1800 → 1200 → 1500。**这一段能跑下来，说明底盘和舵机在一条时间线上是配合得到的**，后面接机构才有基础。

我们留了三段录像在 [docs/videos](videos/README.md)，原声没剪。

## 十、设计上的几个决定

这一节只记「为什么这么选」，具体推导在各自的文档里。

### 麦轮解算：限幅改成整体归一化

四个轮子的速度是算出来的：`lf = vy + vx + ω`、`rf = vy − vx − ω`、`lb = vy − vx + ω`、`rb = vy + vx − ω`（符号按安装方式定）。算完要限幅，不然会超出占空比范围。

我们最初是**每个轮子各自限幅**——超了就压到 1000。这个做法在斜着走的时候会让四个轮子的比例关系被破坏，车就走歪；转弯的时候会画弧，转不圆。改成**整体等比缩放**（四个轮子里最大的那个超了，就按它的比例把其余三个一起缩），才走直。这一步改完，横移和自转同时变好了，因为它们是同一个原因。

推导和验证过程在 [03 底盘运动与麦轮防滑](03_底盘运动与麦轮防滑.md)。

### 两台车，两种轮子

1 号车用麦轮，2 号车用橡胶轮。理由很实在：没有任何一种轮子同时做到「全向精确」和「爬陡坡」。麦轮在地胶上的摩擦系数只有 0.5 到 0.7，而 26.57° 的坡刚刚需要 0.50，几乎没有余量；橡胶轮摩擦够，但横移不了。所以让两台车各拿一头。

2 号车最后没做出来，这个分工的收益也就没能验证。**如果重来，我会先把两台车都做成能跑的基础底盘，再谈分工。**

### 半自动不走视觉，走机械对中

V 型口加两个微动开关。理由是对中失败的模式是「没对准」，重来一次就行；视觉失败的模式是「对准了错的目标」，既费时间又可能撞车。对新手队来说，前一种失败可恢复，后一种不可。

### 机械臂选柱坐标

θ 回转 + Z 升降 + 夹爪开合，三个自由度解耦，不用做逆解，PS2 直接控舵机角度。代价是工作空间是个圆柱，不是球，够不到的地方要挪车。

推导在 [机械臂构型_柱坐标对比](机械臂构型_柱坐标对比.md)，出好的图纸和 STEP 在 [3D打印交付](../3D打印交付/)（`图纸集_结构件.html`、`图纸集_外观套件.html`）。

### 打印件和外购件配合一律做槽，不做孔

甲板上的十字槽配 M3 大垫片（外径 8~10）和 2.5 扎带，装的时候不用量。孔一旦打偏整块板就废了，槽还有调整余地。这条是从第一批孔全偏小那次学来的。

## 十一、踩过的坑

按「现象 → 原因 → 怎么办」写。前面几节里已经说过的不重复，这里放的是还没说的。

### 官方材料在真实场地上不一定够用

物资表里的东西是配套的，但它们不是按真实场地的条件配的。到了场地会发现两件事同时发生：

一是地面比平时练的地方滑。麦轮在地胶上的摩擦系数大约 0.5 到 0.7，横移时轮子容易打滑、对位对不准。

二是负载一上来电压就塌。四轮堵转是 4.8~6 A，而电池盒的弹簧片大约只能过 2 A、26AWG 杜邦线大约 1 A。平时轻载看不出来，一顶到墙、一上坡，电压就掉下去，程序没问题但车没劲。

**怎么办**：赛前一定要去真实场地跑一次，别只在平时练的地方测。带万用表，在车顶住墙的那一瞬间量 `VM`——如果从 8 V 掉到 6 V 以下，就是这条线撑不住，换粗线、换能过大电流的接插件。备件也要带够，见下一条。

爬坡那次的完整诊断在 [坡道上不去与功率不够](坡道上不去与功率不够_诊断与对策.md)——扭矩、摩擦、电压、电流四条都算过了，最后结论是这一套硬件在这个坡上没有余量，不是调参能救的。

### 接线用同色杜邦线，一条线路一个颜色

杜邦线套装通常就一两种颜色，接完一排之后四根信号线长得一模一样。要拆开查其中一根，只能一根根拔下来通电试，试错成本很高；更麻烦的是重接回去时容易插错位，而插错位可能直接把模块送走。

**怎么办**：**一条线路用同一种颜色**，正负极固定红黑，信号线按用途分色（PWM 一个色、方向一个色、片选一个色）。买线时直接买分色套装，比自己剪省事得多。接线之前先在图上把颜色标好，接的时候照着标——插错一眼就能看出来。示波器或万用表去夹的时候也不容易夹错。

### 材料要按「会坏」来备

比赛日程是死的，中间没有等快递的余地。一个驱动模块坏了、一根线断了，当天买不到，接下来两天的活就全停。DRV8833 和舵机是两样最容易被折腾坏的东西：接反一次、堵转几分钟，就没了。

**怎么办**：备件清单按「最可能坏的」排——DRV8833 至少多一片、单片机多一块、SG90 舵机多两个（便宜，堵转烧掉很常见）、杜邦线成把买、焊锡多备一卷、螺丝螺母多备一包。这些东西加起来不到一百块，比停两天便宜得多。

同样的道理，**别在临近节点时改接线**。改动要么早做，要么留够复验的时间。线改完到能跑，中间永远有一段你以为不会出问题、实际会出问题的时间。

### 引脚表不是查出来的，是照着板子拍的

这条是给用 AI 辅助的人看的。我们让 AI 生成过一张 DRV8833 的引脚图，它按 datasheet 的顺序排的——`AIN2` 在 `AIN1` 上面、`BO2` 在 `BO1` 上面、丝印写 `nSLEEP` 而不是 `STBY`，还漏了三个 `GND` 和两个 `NC`。拿这张图去接线，必然接错。

**怎么办**：引脚以**实物丝印**为准，拍张照照着写。没实拍、没丝印依据的引脚顺序，一律不采信。AI 给的任何引脚号、寄存器名，都要在手册或板子上核过才算数。

### 面包板不一定是好的

我们那块面包板内部是断的，插上去看着接好了，实际不通。这种故障极难查，因为它「看起来是对的」。

**怎么办**：怀疑接触问题时，先用万用表通断档量一下面包板两端通不通。更省事的办法是干脆不用面包板——连线直接焊，或者用母对母杜邦线套针。我们后来改成焊成一坨再套热缩管，反而更可靠。

### 连体杜邦头拆不开

买到的排线是几根连在一起的，想拆成单根拆不动。当时给的建议是「插到面包板上分」，行不通。

**怎么办**：要么买散装的单根杜邦线，要么用刀把连体头之间的塑料切开（会留下毛刺，剪掉修平）。已有的连体头就整排用在不需要分线的位置，比如一排 GPIO。

### 万用表会骗你

悬空的节点上，万用表能读出 1.0 V、4.65 V 这种看起来很像样的电压，因为表的内阻是 10 MΩ，足以从别处耦合过来一点电荷。

**怎么办**：量电压要在**有负载**的情况下量。怀疑某个点没接上，用通断档量电阻，别用电压档猜。我们查 DRV 的 VM 就是先量出 1.0 V 以为是欠压，后来发现是根本没接。

### PS2 会被自己的代码锁在「配置模式」里

这条最容易被误判成硬件坏了。现象是：接收器接线没问题、灯也正常，但固件里 `valid_frames` 一直是 0，换一块新接收器还是 0，最后只能下结论「接收器是坏的」。

实际原因是 PS2 手柄的协议里有一个配置模式：主机发 `01 43 00 01 00` 进去以后，手柄就不再回正常的按键帧，必须收到完整的 9 字节退出序列（`01 43 00 00` 加五个 `5A`）才回到轮询模式。中间任何一步没收全，它就停在里面，此后轮询拿到的第二字节不是 `5A`，被判无效——跟真坏了一模一样。

我们原来的代码是这么写的：

```c
if (allow_config && (!valid || out->mode == 0x41u) && due(...))
```

那个 `!valid` 是关键：**读不到有效帧也会触发配置事务，而且每 2 秒重试一次**。链路本来就不通的时候，配置命令其实也到不了；可一旦某次 `enter` 被收到了、紧接着的 `leave` 丢了，接收器就留在配置模式里，再也出不来。

更麻烦的是：ST-LINK 烧录完只复位单片机，接收器一直是带电的，**它不会跟着复位**。所以「重新烧一遍」救不了它，看起来就像烧什么都没用。

**怎么办**：三条一起做。

1. 配置事务的触发条件只留「确实读到了有效帧、但手柄处在数字模式」，不要因为读不到就发。
2. 上电第一帧无条件发一次 `leave`。这条命令只退出、不进入，怎么发都不会把接收器推进去，是安全的。
3. 事务一旦开始就强制走完四步，别中途因为「车开始动了」而停在半路——停在 `enter` 之后是最坏的情况。

判断方法很简单：**真断电重上电能恢复的是被锁，断电也恢复不了的是硬件**。注意断电要拔电池，只按复位键不算。


无线继电器分两种：点动式（按住通电、松手断电）和自锁式（按一下切换）。我们拿到的是点动式，结果「按住才供电，一松手整车断电」，跟预期完全不一样。

**怎么办**：拿到先单独测——不接车，只接一个灯，按一下松手，看灯还亮不亮。点动式的模块上一般有 `T` / `L` 跳线帽或者 `KEY/SW` 按钮可以切模式，切换方法看模块说明书。手册要求这个件要过检录，别到最后才发现模式不对。

### 别把「预案」写成「实测」

文档里凡是标 `【待实测】` 的，都是算出来或者抄来的设计值。量过之后必须换成真实数据——尺寸、重量、成本这三样尤其，因为它们直接对着规则红线。我们交中期材料的时候还有一批数是设计值没回填，这一条写在 [十四、我们没做成的部分](#十四我们没做成的部分) 里了。

**怎么办**：分四类写——实测、推算、预案、未验证。同一份文档里混着写没关系，标清楚就行；不标才是问题，因为你自己过一个月也分不清哪个数是量的、哪个是算的。

### 中期考核的分数是「做到的人平分」

这是规则里的机制，不是技术问题，但影响策略很大：每道题的 100 分由**实际做到并申报的队伍平分**，所以越早交分越高，晚交的人分已经被摊薄了。而且做不到的不报不扣分——**没把握的不要硬报**。

**怎么办**：先把基础题全部做完再报，进阶题最多报 3 项，且必须是真跑通的。爬坡不能报进阶。提交只发邮件、不交实物，截止时间是硬线。

## 十二、组队上的坑

技术之外，这一段大概是这篇里最值钱的。

### 规矩要在开工第一周立，不要等到出问题了再谈

这条是我们自己最想补的一条。项目早期大家都在兴头上，谁也没觉得需要谈规矩；到中后期任务压上来，「谁负责什么」「东西放哪」「文档谁写」「钱谁垫」这些事一件件冒出来，每次都要重新商量一遍，很耗人，也容易积怨。

**建议第一周就把这几条定下来并写进群里**：

- **固定到岗时段**。写清楚哪几天、几点到几点，谁不来要提前说。比「有空就来」有用得多。
- **文档谁写、什么时候写**。最靠谱的做法是**谁做的功能谁写那一节**，做完当天写，别攒。攒到最后一定变成一个人替五个人回忆。
- **工具和材料的位置**。焊台、螺丝刀、剪钳用完归位，耗材放在固定的盒子里。丢一把剪钳能耽误半天。
- **钱怎么走**。谁垫付、怎么报销、发票谁收。我们是队长统一垫、统一开票，好处是账目清楚，坏处是垫的钱多。
- **谁签字、谁对检录负责**。尺寸、重量、成本这几个数必须有一个人最终确认，不能「大家都觉得没问题」。

### 工作时间要提前磋商，不要临时问

「你今晚有空吗」这种问法，一个项目里问几十遍，消耗掉的时间比想象中多。而且对方回「有空」的时候，往往还要再花时间想清楚自己要带什么东西来。

**怎么办**：每周固定一次十分钟的短会，把下一周的时段排出来，写在群公告里。临时要加，提前一天说。这样每个人都能安排自己的课和其他事，也不会出现「五个人到场，只有两个人在干活」。

### 分工要按「交付物」分，不要按「领域」分

按领域分（你做电控、我做机械）听起来合理，实际会出现「机械做完了但没人装配」「电控写完了但没人接线上车」这种空档。

**怎么办**：分工落到具体交付物上，比如「底盘能前进后退走直线」归一个人、「电源三路主干接完并通过上电检查」归一个人。每件事都有名字，就不会掉在地上。

### 一个人干太多的信号

如果你发现自己连续三天在做别人的部分，说明分工已经失衡了，要当场提出来，不要扛到赛后。这不是抱怨，是工程问题——单点依赖在任何项目里都是风险。

## 十四、我们没做成的部分

写清楚这个，是为了让下一个人不要以为抄过去就一定能成。

**2 号车没有实物。** 方案、尺寸、轮子选型都定了，底盘没做出来。所以我们说的「两台车分工」是纸上的分工。

**机械臂没打印。** 八件的模型、STEP、运动范围校核全做完了，切片没跑，装配没试。那套柱坐标构型的推导应该是成立的，但没有实物验证过。

**麦轮公式用得起来，但推不出来。** 逆解那四个式子是照着开源项目用的，符号怎么定的、为什么是这四项，我说不清楚。这不是「大概理解」，是真的推不出来。想深入的人得自己去补理论。

**PID 没做。** 全程开环，速度靠标定，走直线靠机械对称。能跑，但一有负载变化就偏。闭环是下一步该做的。

**视觉只有备选代码。** `vision/k210_find_cube.py` 是色块识别，没上车跑过。

**无线继电器是点动式的，最后没切成功。** 这个直接影响检录，是我们没收干净的一条。
